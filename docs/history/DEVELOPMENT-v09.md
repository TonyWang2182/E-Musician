# E-musician 开发计划

文档版本：0.9。更新日期：2026-10-27（Asia/Shanghai）。项目位置：`E:/E-musician/`。

当前工作是 **0.4.0 通用 DAW 基础功能的最终验收**。本轮功能已实现，已建立同一源码下Debug与Release各4/4通过的自动回归基线；原生截图复核及部分实际插件、JSONL任务、密集MIDI测量已有证据。后续CNG/SHA-256性能优化仍须按新源码回归，最终OS操作、插件兼容与长跑未全部收口，不能把局部通过等同完整交付。最新状态集中在 [CONTEXT](../CONTEXT.md)，逐项范围及证据见 [DAW_BASELINE](../DAW_BASELINE.md)。此前0.3.0的证据仍只覆盖当时功能。

## 1 本轮确定范围

用户要求先获得可以使用的 DAW 基础，并为后续 Agent 留真实接口。最新要求接替先前参考UI中的和弦/模板规划：

- 不做和弦工具、确定性乐句模板或自有音源库。
- 新工程默认120 BPM、4/4；固定速度20–300 BPM，默认1/16网格，可关闭吸附。
- Windows x64 VST2与VST3均纳入；MIDI通过用户已安装的插件发声。
- 完成音频编辑、工程保存恢复、基础混音/循环、WAV输出、MIDI编辑和SMF读写。
- 文件操作后台准备，可显示进度、取消、拒绝晚到冲突结果；普通编辑/对应Undo保持播放和无关插件实例。
- Agent先获得可查询、可执行、可重试的本地接口与实际客户端；本轮不增加空聊天面板或模型占位流程。
- 性能结论必须来自实际配置和负载，不能用技术栈、轨道上限或一次启动代替测量。

录音、32位插件桥接、复杂路由/侧链、多输出乐器、自动化曲线、TempoMap、音频拉伸、真实分离/转录模型、模型Agent及跨平台发布不在本轮。ASIO当前关闭，驱动支持和低延迟矩阵需另验收。自动保存/完整崩溃恢复、缓存及旧归档安全清理不能由已有事务保存推断完成。

### 当前用户闭环

导入WAV/MP3或MIDI → 在Compose查看全部轨道 → 移动/裁剪/分割/复制片段，调整混音 → 编辑MIDI并加载乐器 → 保存重开 → 导出WAV/MIDI。也可从空MIDI轨开始，不要求先分析音频。

后续产品方向仍保留 Separate → Transcribe → Compose：真实分轨和转录结果经过用户接受，成为同一工程里的音频或MIDI片段。当前Separate仅检查选中音频源，自动Transcribe未接入。参考图中的unit~、112 BPM、24秒、64 notes等是历史示意，不是应用默认值或测试通过证据。

### 技术与人员

C++20 + 固定Tracktion3.2.0提交 + JUCE8.0.6承担桌面核心。VST2使用本地固定历史接口头，VST3使用固定JUCE内附接口；来源、哈希和许可文本记录在 [DEPENDENCIES](../DEPENDENCIES.md)。应用播放不需要Python、FFmpeg或模型服务；Python客户端/测试和测试素材编码器有各自边界。

用户负责创作优先级、真实设备及音乐听感反馈；开发代理负责实现、构建、故障复现、性能证据和文档。出现具体驱动/DSP/插件问题时再引入专项检查。当前基础功能不依赖付费模型调用；尚未选定远程Provider、预算或音频上传范围。

后续Provider选型必须记录：能力、代码/权重版本、输入限制、时间基准、取消、运行环境、冷启动/计算耗时、峰值RAM/VRAM、质量样例、费用与部署方式。不能默认当前Python或GPU适合任何模型。

## 4 技术组合与边界

实际模块细节维护在 [ARCHITECTURE](../ARCHITECTURE.md)，协议在 [AGENT_API](../AGENT_API.md)。本轮架构选择见 [ADR0005](../decisions/0005-daw-baseline-and-control.md)。

| 组件 | 依赖与组合 |
|---|---|
| 原生UI | 读取只读Snapshot，按稳定ID发命令；不直接写Edit |
| EngineSession | 单写控制入口；候选校验、增量应用、Undo、revision和事件 |
| Tracktion Edit | 活动音乐权威；音轨、片段、MIDI、插件链与Transport |
| 引擎音频图 | 按引擎线程契约播放；不运行JSON、文件、网络或模型工作 |
| AudioSource/ProjectStorage | worker处理准备源和归档；不拥有可写活动工程 |
| PluginHost | 隔离扫描、主线程实例/窗口/状态；播放中的插件仍在宿主进程 |
| WAV render worker | 固定快照、独立进程、临时输出；父进程验证后替换目标 |
| ControlServer | 有界JSONL输入输出和主线程分发；与GUI共用命令语义 |
| 未来模型服务 | 只产生候选，接受后提交命令；不得覆盖期间的手工编辑 |

新建/打开可以替换Edit；普通编辑及Undo保持同一Edit和无关插件实例。ValueTree事务保存音乐状态和应用ID，音量/声像/loop及外部参数使用显式标量Undo。插件删除前缓存可恢复原生状态与必要参数投影，不通过长期保活所有已删除实例实现Undo。停止播放时组件状态和控制器参数可能不同步，必须验证延迟Undo与保存重开的实际参数，不能只比较二进制块是否存在。

密集MIDI使用按片段失效的共享只读音符快照与内容摘要；无关混音命令不遍历全部音符，小批改动通过稀疏edit_notes路径处理。音符批量构造避开逐个线性查找，UI复用未变化的快照并用ID差集提交。Windows CNG SHA-256用于降低完整内容摘要的控制线程开销，与参考摘要的一致性检查随新构建回归；缓存和摘要都不是第二个可写音乐模型。

文件导入/打开只在启动时的工程身份和revision仍匹配时提交。保存/导出使用固定快照；晚到保存不清除后续修改。单个重文件任务限制I/O/CPU并发，波形准备单独缓存。任务completed必须在主线程提交后发布，不能把线程结束或accepted当完成。

协议只显式开启本地stdio，不监听网络。写请求携带request_id/project_id/expected_revision；快照不包含全部音符，片段、音符、目录和参数分页。单帧1MiB、队列32项、事件1024项、任务历史64项和外部幂等账本10000项均有界，内部revision推进不累积随机请求ID。全量write_notes的100000音符上限仍受stdio帧大小约束，大片段通过edit_notes局部upsert/delete。音乐调度不通过这些控制队列。

### Remote Scripts资料的启发

用户提供的 [Structure Void](https://midiremotescripts.structure-void.com/) 与 [gluon仓库](https://github.com/gluon/AbletonLive12_MIDIRemoteScripts) 用于学习控制面分层、模式/映射、属性监听、反馈和断开清理。此前检查的社区源码基线为 [e83d5192f321b24eb9daab843ac49a2d95d862b1](https://github.com/gluon/AbletonLive12_MIDIRemoteScripts/commit/e83d5192f321b24eb9daab843ac49a2d95d862b1)，不是官方独立SDK，也不是本项目音频引擎。

本项目对应采用“连接适配 → 领域命令 → Edit”的分层、操作后结果回读、稳定ID与版本、批次Undo及生命周期测试。未来Live适配分别核对Python Remote Script和M4L能力；普通Python不能直接使用宿主内`Live`运行时，社区12.4标签也不保证每项12.4.3行为一致。

## 6 性能目标与测量

### B01基础音频

在本机接电状态记录系统、后台负载、设备和驱动。目标48kHz/256samples，16条独立立体声WAV，预热2分钟，再测30分钟；无第三方插件的基线与具体插件负载分开。设备不支持256时记录实际值和目标未测，不用480等实际缓冲冒称256通过。

| 指标 | 目标或记录方式 |
|---|---|
| 回调耗时 | 目标P99.9低于块预算80%，超预算次数为0；均值不能替代尾部统计 |
| XRun/中断 | 可观测欠载目标0；记录计数来源，无法观测的项目写未测 |
| 控制响应 | 常见交互P95目标小于50ms，说明是命令dispatch、定时器延迟还是物理输入到绘制 |
| 内存 | 预热后趋势、峰值、重复开关/编辑后的残留；解释历史/缓存增长与泄漏的区别 |
| 状态 | 播放中编辑/Undo保持Transport和无关实例；保存重开内容一致 |
| UI/磁盘 | 播放时缩放、滚动、编辑和后台任务分别测试，不用纯音频负载代替全部场景 |

当前性能探针采用Tracktion实际callback count/mean/min/max/stddev、设备CPU/XRun、控制线程定时/编辑耗时及进程内存。没有逐回调样本就将P99.9标为unavailable，没有物理输入测量就不宣称该项达标。探针执行成功、实际配置下部分指标通过和B01全部目标通过是不同结论。

### B02分析与 B03界面/密集MIDI

后续模型基准记录短授权样本的冷启动、耗时、峰值RAM/VRAM、输入输出对齐和取消，再与基础播放并行；质量以有真值旋律和人工试听分别评估起音/时值/音高误差、漏音/多音及伪影，不以任务成功率代替。

B03覆盖最小/常规窗口、DPI、长名称、滚动、多片段和密集MIDI。100000音符是保护上限；必须另测连续增益/参数编辑、快照和UI开销，16轨WAV不能证明此负载。新增诊断耗时属于对应控制线程操作，不解释为音频回调时延。

已记录的 [100000音符Release控制测量](../builds/20261026T170525.513639Z-4f33e20459.json) 使用源码 `4053c3e…`，停止Transport且不加载插件，通过原JSONL管道往返。P95为声像11.03ms、快照11.27ms、单音符修改49.71ms，导入3.98秒，单音符Undo/Redo通过；满足脚本原定50ms预算。其前一版 [失败记录](../builds/20261026T165129.275940Z-7f8e7cb864.json) 保留，未降低验收门槛。此证据仅关闭该控制负载的当前问题，不代替物理输入到绘制时延、边播放边编辑、插件负载或长时间内存稳定性。

每份报告记录源码指纹、依赖、构建配置、系统/CPU/RAM、设备/实际缓冲、素材与插件负载、方法、原始结果和复现命令。若目标或方法改变，追加决策与说明，保留原失败数据。

## 8 重要风险与后续决定

| 风险或决定 | 当前处理 |
|---|---|
| 参数和Transport setter不自动记录Undo | 明确增益/声像/loop/插件参数的标量Undo，并检查真实状态与音频恢复 |
| 不同采样率渲染产生块边界相位问题 | sincMedium与固定Tracktion HQ源定位补丁共同修复；补丁前后哈希进入清单，256/512块及三格式真实渲染回归通过；升级引擎需重新验证 |
| 插件删除后晚些Undo丢音色 | 删除前缓存原生状态；等待缓存回收后再测恢复，不长期保活实例 |
| 插件扫描/渲染挂起 | 独立worker、超时/取消、有界结果；播放期插件崩溃隔离另做 |
| 主线程或Agent请求过大 | 分页、有界队列、局部音符命令、密集工程实测；不把JSON放音频回调 |
| 晚到导入/保存覆盖新编辑 | 身份/revision重验、固定保存快照、完成后再公布终态 |
| 保存恢复损坏用户工程 | 新代次、临时清单、旧版逐字节备份、失败注入；原工程哈希保护 |
| 驱动或系统调度影响性能 | 记录实际协商配置，区分DSP负载、宿主超时和设备计数 |
| 模型资源争抢 | 后续独立进程和并发限额，B02与B01联测 |
| SDK/许可与发行路径 | 固定来源和原许可文本；本地开发不等于已完成公开分发准备 |

项目品牌保持E-musician，黑白等宽/开放轮廓沿用用户参考；产品行为以最新需求及实际可用性为准。外部Provider、预算/上传范围、发行方式、ASIO与具体设备矩阵、首批插件兼容清单均随对应阶段落实。
